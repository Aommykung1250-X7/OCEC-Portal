# OCEC Portal: เชื่อมฟีเจอร์ที่ยังไม่ทำงานกับ API

## สถานะ

Design สำหรับให้ผู้ใช้ตรวจทาน ยังไม่มีการเปลี่ยน implementation ตามเอกสารนี้

## เป้าหมาย

- ทำให้เส้นทางสมัคร Final ใช้งานได้จริงทั้งกรณีสมัคร Heat เองและกรณีโรงเรียนสมัครให้
- ต่อหน้าจอแอดมินที่ยังไม่มีปฏิสัมพันธ์กับ API เข้ากับ API ที่มีอยู่แล้ว
- เอาข้อความตัวอย่างและวันที่สอบที่เขียนตายตัวออกจาก flow ที่ผู้ใช้ใช้งานจริง
- ทำแผนทดสอบที่ครอบคลุมทุกเมนูและ action สำคัญ โดยระบุ API หรือเหตุผลที่เป็นงานฝั่งเว็บ/ลิงก์ภายนอก

## ข้อกำหนดที่ยืนยันแล้ว

- BBB ใช้รางวัล 1st/2nd/3rd สำหรับสิทธิ์ Final; รายการแข่งขันอื่นใช้ Gold/Silver/Bronze
- ลิงก์แก้สลิปใช้ได้ครั้งเดียว และหมดอายุหลังไม่ได้ใช้งาน 3 วัน
- ปัญหาสลิปของชุดโรงเรียนส่งลิงก์ให้ผู้ประสานงานโรงเรียนเท่านั้น
- รูปเกียรติบัตรและหมายเหตุภายในแอดมินพร้อมประวัติเป็นฟีเจอร์จริง
- หมายเหตุแอดมินแก้ไขและลบได้ โดยเก็บประวัติก่อน/หลัง
- Google Sheets retry อัตโนมัติและมีปุ่ม retry สำหรับแอดมิน
- สถานะสาธารณะแสดง “ไม่อนุมัติ” พร้อมเหตุผลสั้น ๆ; การปฏิเสธส่งอีเมลถึงผู้สมัครด้วย
- การเรียงเลข Heat ใช้ชื่อจริง ชื่อกลาง นามสกุลภาษาอังกฤษตามลำดับ A–Z
- ทดสอบ Gmail, Drive และ Sheets ด้วย HTTP mocks; ไม่ใช้บัญชีบริการจริง
- ติดต่อฝ่ายช่วยเหลือผ่าน LINE OA OCEC_Thailand ที่ https://lin.ee/3hzFg1z
- Final จากใบสมัคร Heat ที่สมัครเองต้องใช้ Google account เดิมที่เป็นเจ้าของ Heat
- Final จากใบสมัคร Heat ที่โรงเรียนส่ง ผู้สมัครยืนยันชื่อ รายการสอบ และโทร 4 ตัวท้าย แล้วใช้ Google account ใดก็ได้ที่ผู้สมัครเลือก; ใบสมัคร Final เป็นของบัญชีนั้น ส่วน Heat ยังเป็นของผู้ประสานงาน

## ข้อเท็จจริงจาก source ปัจจุบัน

- Google OAuth, `/api/applications/submit`, การตรวจรางวัลและ `final_invitations` มีแล้ว แต่ไม่มี public API สำหรับค้นและยืนยันสิทธิ์ Final
- การตรวจ Final ใน `resolveDraft` ผูก Heat กับ `owner_user_id` ปัจจุบัน จึงปฏิเสธผู้สมัครที่ Heat เป็นของผู้ประสานงานโรงเรียน
- หน้าค้น Final พึ่งรายการสมัครใน browser และยังมีเส้นทางสมัครแบบ guest
- API หมายเหตุแอดมิน, API ปฏิเสธใบสมัคร, API สถานะสาธารณะและ API เปลี่ยนสลิปมีแล้ว แต่หน้าจอใช้ไม่ครบ
- หน้า admin slip-upload ยังแสดงความสำเร็จจาก state ฝั่งเว็บ ส่วนเส้นทางอัปโหลดผ่านลิงก์ใช้ครั้งเดียวมี API แล้ว
- เมนูช่วยเหลือแสดงข้อความ prototype; วันสอบและปีบางจุดเขียนตายตัว
- การเพิ่ม/แก้ catalog ทำใน state ก่อน และบันทึกลงฐานข้อมูลผ่านปุ่มบันทึก catalog ที่เรียก API อยู่แล้ว
- หน้า Google Sheets มี API ตรวจสถานะ, คิว retry อัตโนมัติ, ปุ่ม sync และปุ่ม retry งานที่ล้มเหลว

## แนวทางที่เลือก

ทำการยืนยันสิทธิ์และผูกบัญชีเฉพาะ Final โดยเก็บเจ้าของ Heat เดิมไว้ ไม่ย้ายหรือโอนใบสมัครโรงเรียนทั้งหมดให้ผู้สมัคร

ระบบค้นหาและยืนยันสิทธิ์จะอ้างผล Heat ที่ประกาศแล้วและสิทธิ์ Final ที่ยังเปิดอยู่เท่านั้น ก่อนยืนยัน ระบบเปิดเผยเฉพาะข้อมูลรายการสอบที่จำเป็นต่อการเลือก เช่น รายการแข่งขัน รอบ และปี ไม่เปิดชื่อเต็ม โรงเรียน เบอร์โทร อีเมล หรือ ID ใบสมัคร หลังผู้สมัครยืนยันโทร 4 ตัวท้ายสำเร็จ ระบบจึงส่งข้อมูลที่จำเป็นต่อการเติมฟอร์ม Final

บัญชีเจ้าของใช้ `owner_user_id` เป็นหลักฐานสำหรับ Heat ที่สมัครเอง กรณีโรงเรียนสมัครให้ backend ออกสิทธิ์ยืนยันที่ผูกกับ Google user ที่ล็อกอินหลังยืนยันโทร 4 ตัวท้าย แล้วตรวจสิทธิ์นั้นซ้ำใน transaction ตอนส่ง Final การยืนยันทาง browser หรือ `allowedRoundIds` จาก client ไม่ถือเป็นหลักฐาน การเชื่อมสิทธิ์และการ claim ต้องป้องกันการใช้ซ้ำและการส่งพร้อมกัน โดย `final_invitations.claimed_application_id` ยังคงเป็นตัวกันการใช้สิทธิ์ซ้ำตอนสร้างใบสมัคร

การยืนยันตัวตนแบบใช้โทร 4 ตัวท้ายต้องจำกัดจำนวนครั้ง มี response ที่ไม่เปิดเผยว่าใบสมัครใดมีอยู่ และใช้ `Cache-Control: no-store` การจับคู่ที่คลุมเครือหรือพบผู้สมัครชื่อเดียวกันมากกว่าหนึ่งคนต้องไม่เลือกให้เอง; แสดงวิธีติดต่อ LINE OA แทน

### ทางเลือกอื่น

1. **แนวทางที่เลือก — claim สิทธิ์ Final เท่านั้น:** การเปลี่ยน schema และสิทธิ์จำกัดอยู่ที่ Final; เหมาะกับกติกาที่ผู้ใช้ยืนยัน
2. **เชื่อมบัญชีผู้สมัครกับใบสมัคร Heat ของโรงเรียนทุกประเภท:** ทำให้ผู้สมัครเห็นและจัดการ Heat เดิมด้วย แต่ขยายสิทธิ์การเข้าถึง ประวัติ รูปเกียรติบัตร และ flow ของชุดโรงเรียนโดยไม่จำเป็นต่อการสมัคร Final

## Flow สมัคร Final

### Heat ที่สมัครเอง

1. ผู้สมัครล็อกอิน Google
2. ระบบอ่าน Heat ที่ผู้ใช้เป็นเจ้าของจาก API และแสดงเฉพาะรายการที่มีผลประกาศและมีสิทธิ์ Final
3. ผู้สมัครเลือกรอบ Final ที่เปิดให้สมัครและกรอกใบสมัครแยกพร้อมชำระเงิน/แนบสลิป
4. backend ตรวจว่า Heat มี `owner_user_id` ตรงกับ session และ invitation ยังไม่ถูกใช้

### Heat ที่โรงเรียนสมัครให้

1. ผู้สมัครค้นด้วยชื่อภาษาอังกฤษ
2. ระบบแสดงรายการสอบที่ตรงกับชื่อและมีสิทธิ์ Final ให้เลือก โดยไม่แสดงข้อมูลส่วนตัวหรือข้อมูลโรงเรียนก่อนยืนยัน
3. ผู้สมัครกรอกโทร 4 ตัวท้าย; backend ตรวจชื่อ รายการสอบ สิทธิ์ รางวัล กำหนดเวลา และสถานะ invitation
4. backend ออก verification grant ฝั่ง server ที่ผูกกับ invitation และ OAuth attempt; ห้ามใส่ PII หรือสิทธิ์ที่เชื่อถือได้ไว้ใน client state
5. ผู้สมัครล็อกอิน Google ด้วยบัญชีที่เลือก; OAuth callback ผูก grant กับ user จาก Google หลังตรวจ state, nonce และ session ตาม flow เดิม
6. ระบบเติมข้อมูลผู้สมัครจาก Heat ให้ตรวจและแก้ในฟอร์ม Final; การ submit เรียก API เดิมโดยส่ง source Heat และใช้ user ที่ล็อกอินเป็นเจ้าของ Final
7. backend ตรวจ claim และสร้าง Final ใน transaction; การ submit ซ้ำหรือแข่งกันใช้ invitation เดียวกันสร้างได้เพียงหนึ่งใบ

การยืนยันต้องกลับมาทำใหม่ได้เมื่อ grant หมดอายุหรือ OAuth ถูกยกเลิก โดย invitation ยังไม่ถูกใช้จนกว่าจะส่ง Final สำเร็จ ผู้สมัครที่เลือกบัญชีผิดสามารถออกจากระบบและเริ่มยืนยันใหม่ด้วยบัญชีที่ต้องการได้

## การเชื่อมหน้าจอที่ API มีแล้ว

### ตรวจใบสมัครและสลิป

- เพิ่ม action ปฏิเสธพร้อมเหตุผลสั้น ๆ; ใช้ `PATCH /api/admin/applications/:id/review` ด้วย `decision: reject`
- กำหนดให้เหตุผลไม่ว่างใน UI และ API สำหรับการปฏิเสธ; จำกัดความยาวตาม schema ปัจจุบัน
- แสดงเหตุผลจาก `GET /api/public/applications/status` ในผลค้นหาสาธารณะ และคงการส่งอีเมลจาก backend
- เปลี่ยน admin slip-upload ที่เป็น prototype เป็น action สร้าง/ส่งลิงก์ใหม่ด้วย `decision: slip_issue`; การสร้างใหม่เพิกถอนลิงก์เดิม
- ชุดโรงเรียนส่งอีเมลถึง coordinator เท่านั้น; ผู้รับลิงก์อัปโหลดผ่าน endpoint validate/submit ซึ่งปฏิเสธ token หมดอายุ ใช้แล้ว หรือไฟล์ไม่ถูกต้อง

### หมายเหตุภายในแอดมิน

- ในหน้าตรวจใบสมัคร โหลด/เพิ่ม/แก้/ลบหมายเหตุผ่าน `/api/admin/applications/:id/notes`
- แสดงผู้เขียนและเวลาของหมายเหตุ; มีมุมมองประวัติจาก `includeHistory=true`
- เฉพาะแอดมินอ่านและแก้ได้; public lookup, ผู้สมัคร และอีเมลไม่เห็นหมายเหตุ

### การช่วยเหลือ ตารางสอบ และ catalog

- เปลี่ยนเมนูช่วยเหลือทั้งหัวและท้ายหน้าเป็นลิงก์ LINE OA ที่ระบุ พร้อมเปิดในแท็บใหม่อย่างปลอดภัย
- ใช้ `examDate` และ `year` จาก catalog API สำหรับวันสอบ/รอบสอบ/ข้อความปีการศึกษา; ถ้าไม่มีรอบที่จะนำเสนอ ให้ลิงก์ไปหน้ารายการสอบแทนวันที่ตัวอย่าง
- แสดงสถานะ catalog ที่ยังไม่ได้บันทึก และเตือนก่อนออกจากหน้าหากมีการแก้ไขค้าง; ทดสอบว่าบันทึกแล้วโหลดหน้าใหม่ยังได้ค่าเดิม
- การ export Excel และการนำทางที่ไม่เปลี่ยนข้อมูลคงเป็นงานฝั่ง browser; ไม่สร้าง API เพิ่มโดยไม่มีข้อมูลหรือ action ที่ต้อง persist

## ขอบเขต

- ไม่สร้างระบบ ticket/FAQ หลังบ้าน; ช่องทางช่วยเหลือใช้ LINE OA ตามที่ผู้ใช้เลือก
- ไม่โอนเจ้าของใบสมัคร Heat ของโรงเรียน และไม่เปิดสิทธิ์บัญชีผู้สมัครให้เข้าถึงใบสมัคร/ข้อมูลอื่นของ coordinator
- ไม่เปลี่ยน Google Workspace ให้เรียกบริการจริงในการทดสอบ
- ไม่สร้าง API ใหม่สำหรับ export ที่สร้างไฟล์จากข้อมูลซึ่งโหลดจาก API อยู่แล้ว
- หน้าตัวอย่างที่ยังเก็บไว้ต้องเป็น read-only และต้องไม่แสดงผลสำเร็จจากการบันทึกจริง

## การทดสอบและเกณฑ์ตรวจรับ

เพิ่ม traceability matrix ให้ทุก route/action หลักในเมนูระบุหนึ่งใน: API และ test case, ลิงก์ภายนอกและ URL, หรือการทำงานฝั่ง browser ที่ไม่ persist พร้อมเหตุผล

### Final และตัวตน

- ค้นหาไม่คืนผู้สมัครที่ไม่มีผล, ยังไม่ประกาศ, ไม่ได้รางวัลที่มีสิทธิ์ หรือปิดรับสมัครแล้ว
- BBB ยอมรับเฉพาะ 1st/2nd/3rd; รายการอื่นยอมรับเฉพาะ Gold/Silver/Bronze
- เลือกรายการสอบก่อนส่งโทร 4 ตัวท้าย; ชื่อ/รอบ/เบอร์ผิด, ชื่อซ้ำหรือผลค้นหาคลุมเครือไม่เผย PII และไม่ออก claim
- ผู้สมัคร Heat เองส่ง Final ได้จากบัญชีเจ้าของ Heat; บัญชีอื่นถูกปฏิเสธ
- ผู้สมัครจากโรงเรียนใช้ Google account ที่เลือกได้หลังยืนยันถูกต้อง; Final เป็นของ user นั้นและ Heat ยังคงเป็นของ coordinator
- OAuth state/nonce ผิด, ยกเลิก, หมดอายุ หรือ replay ต้องไม่ผูก claim; claim ใช้แล้วหรือมี concurrent submit ต้องได้ Final เพียงใบเดียว
- ปิดทดสอบการสมัคร Final แบบ guest และป้องกันการ submit โดยอาศัย client state อย่างเดียว

### หน้าจอและ workflow อื่น

- แอดมินเพิ่ม/แก้/ลบหมายเหตุ; ประวัติเก็บค่าก่อน/หลัง actor/time; ไม่มี API สาธารณะคืนหมายเหตุ
- แอดมินปฏิเสธพร้อมเหตุผล; ค้นสถานะพบ “ไม่อนุมัติ” พร้อมเหตุผลสั้น และอีเมลแจ้งผู้สมัครมีเหตุผลเดียวกัน
- resend slip ออก token ใหม่ เพิกถอน token เดิม ส่งถึง coordinator สำหรับ school batch, ใช้ได้ครั้งเดียวและหมดอายุใน 3 วัน
- public status และ certificate photo ใช้สิทธิ์และ cache policy ที่กำหนด; Sheets auto-retry และ manual retry คงทำงาน
- ลิงก์ช่วยเหลือเปิด `https://lin.ee/3hzFg1z`; วันสอบบนหน้าเว็บมาจาก API และปรับตาม catalog หลัง reload
- catalog ที่ยังไม่กดบันทึกแสดงสถานะค้าง; กดบันทึกแล้วค่าคงอยู่หลัง reload; validation และ API failure แสดงข้อผิดพลาดโดยไม่กล่าวว่าบันทึกสำเร็จ
- ทุก action ที่เปลี่ยนข้อมูลตรวจ response API ก่อนแสดง success; ไม่มี fake success ใน production mode

### ชั้นทดสอบ

1. Pure rules: การเลือกสิทธิ์, การ normalize ชื่อ/โทรศัพท์, วันเปิด/ปิด, การแสดงสถานะ และข้อความอีเมล
2. API contract: schema, status code, auth, no-store, rate limit, error mapping และ response ที่ไม่รั่วข้อมูล
3. PostgreSQL workflow: claim, owner, transaction, duplicate/concurrency, migration และ audit
4. Browser end-to-end: Heat เอง, Heat โรงเรียน, OAuth mock, ตรวจ/ปฏิเสธใบสมัคร, หมายเหตุ, resend slip, catalog และเมนูช่วยเหลือ
5. Google provider adapter ใช้ HTTP mocks เท่านั้น

โปรเจกต์ยังไม่มี browser test harness; เพิ่ม harness สำหรับเส้นทาง end-to-end โดยใช้ test database แบบ disposable และ OAuth/Google provider mocks ห้ามชี้การทดสอบไปฐานข้อมูล production หรือบริการ Google จริง

## ลำดับ implementation หลังอนุมัติ spec

1. เพิ่ม/ปรับ acceptance tests และ traceability matrix รวมทั้งแก้ test decisions ที่เก่ากว่าให้ตรงกับข้อยืนยันล่าสุด
2. ทำ Final search, verification grant, OAuth continuation, owner policy และ transaction การ claim
3. เชื่อมหน้าจอปฏิเสธ/เหตุผล, หมายเหตุ และ resend slip กับ API เดิม
4. เปลี่ยน LINE help, วันที่ที่ hardcode และสถานะ unsaved catalog
5. ทำ browser flows และรัน pure/API tests, disposable database suite, browser suite และ production build
