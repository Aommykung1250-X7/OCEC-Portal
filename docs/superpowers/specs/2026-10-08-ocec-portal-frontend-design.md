# OCEC Portal Front-end Design

สถานะ: สร้างต้นแบบแล้ว
วันที่: 8 ตุลาคม 2026

## เป้าหมาย

ทำ front-end prototype ที่เปิดดูและกดเดิน flow หลักได้ โดยอ้างอิงหน้าและกติกาจาก OCEC-Portal-Requirements.md ให้ครอบคลุมผู้สมัคร ผู้ประสานงาน บุคคลทั่วไป และแอดมิน ใช้ข้อมูลตัวอย่างในเบราว์เซอร์เพื่อแสดงสถานะและ feedback โดยยังไม่เชื่อม backend, Google Sign-In, SMTP, Google Sheets หรือระบบนำเข้าไฟล์จริง

## แนวทางที่เลือก

ใช้ React + Vite เป็น single-page prototype แบ่งหน้าตามกลุ่มงาน และเปลี่ยนหน้าผ่าน navigation ภายในแอป ไม่ติดตั้ง component framework เพิ่ม ใช้ CSS และ reusable React components สำหรับ header, form controls, status badges, cards, tables และ admin navigation ข้อมูลตัวอย่างอยู่ใน frontend และ state เปลี่ยนได้เฉพาะเพื่อสาธิต flow

ข้อดีคือครอบคลุมหน้าจำนวนมากได้ด้วยโครงสร้างร่วมกันและทำให้ผู้ใช้ลอง interaction ได้เร็ว ส่วนการเชื่อมบริการจริงและความปลอดภัยของข้อมูลอยู่นอกขอบเขตนี้

## ผู้ใช้และรายการหน้า

### หน้าสาธารณะ

- หน้าแรกสาธารณะ: แสดงรายการที่เปิดรับเป็นการ์ดแยกรายการ เห็นวันปิดรับและปุ่มสมัครตรงรายการ รองรับหลายรอบพร้อมกัน; มีวิธีสมัครสามขั้นตอนและทางลัดค้นหาสถานะ/ประกาศผล
- เลือกวัตถุประสงค์ค้นหา: แยก “ค้นหาสถานะ” กับ “แก้ไขข้อมูลใบสมัคร” ให้ชัดก่อนเปิดฟอร์ม
- ค้นหาสถานะ: ไม่ต้องเข้าสู่ระบบ ค้นจากชื่อภาษาอังกฤษและแสดงเฉพาะสถานะทั่วไป “รออนุมัติ/ตรวจสอบสลิป” หรือ “ยืนยันใบสมัคร”
- ยืนยันตัวตนเพื่อแก้ไข: ชื่อภาษาอังกฤษและเลข 4 ตัวท้ายของเบอร์ในใบสมัคร จากนั้นเปิดรายละเอียดที่แก้ไขได้
- อัปโหลดสลิปใหม่: หน้าจากลิงก์เฉพาะ แสดงเฉพาะการแนบสลิป และสาธิตการใช้ลิงก์ครั้งเดียว
- ยืนยันสิทธิ์ Final: ค้นชื่อภาษาอังกฤษ เลือกผลที่มีเลขสอบ/ชื่อ/โรงเรียนตรงกัน ยืนยันด้วยเลขท้ายโทรศัพท์ แล้วเลือกผูกบัญชี Google หรือทำต่อโดยไม่เข้าสู่ระบบ
- สมัครสอบ: ฟอร์ม Heat และฟอร์ม Final แยกกัน เลือกสมัครในนามตนเองหรือโรงเรียนได้ เก็บอีเมลติดต่อผู้เข้าสอบแยกจากอีเมลบัญชี Google; Final แสดงข้อมูลจาก Heat ให้ตรวจและแก้ก่อนส่ง พร้อมส่วนแนบสลิปแยก
- ประกาศผลสาธารณะ: ค้นหาผู้ผ่านด้วยชื่อหรือเลขประจำตัวสอบ แสดงผลหลังมีการประกาศแล้ว

### พื้นที่บัญชีผู้ใช้และผู้ประสานงาน

- ใบสมัครของฉัน: จัดกลุ่มตามรายการสอบและปี ผู้ประสานงานเห็นผู้เข้าสอบแต่ละคนที่ส่งผ่านบัญชีเดียวกัน
- รายละเอียดใบสมัคร: แสดงชื่อ โรงเรียน เลขประจำตัวเมื่อมี สถานะทั่วไป และข้อมูลตามใบสมัคร
- แก้ไขใบสมัคร: ก่อนอนุมัติเป็นอ่านอย่างเดียว หลังอนุมัติแก้เฉพาะข้อมูลที่อนุญาตและก่อนถึงเวลาปิดแก้ไข โดยล็อก 4 ช่อง รายการสอบ ระดับชั้น รูปแบบสอบ และศูนย์สอบ
- ยืนยันสิทธิ์ Heat ที่ผ่าน: เริ่ม flow ยืนยันสิทธิ์ Final จากใบสมัครในบัญชี
- ผลสอบของฉัน: ผู้ใช้ที่เข้าสู่ระบบเห็นผลทั้งกรณีผ่านและไม่ผ่าน

การเข้าสู่ระบบใน prototype เป็นปุ่มจำลอง Google Sign-In และมีตัวเลือก persona ตัวอย่างเพื่อสาธิตมุมมองผู้สมัคร/ผู้ประสานงาน ไม่เก็บ token หรือข้อมูลจริง ผู้ประสานงานหนึ่งบัญชีส่งหลายใบสมัครได้ โดยแต่ละใบเป็นของผู้เข้าสอบหนึ่งคน

### หลังบ้านแอดมิน

- ภาพรวม: จำนวนใบสมัครที่รอตรวจ สถานะรอบสอบ และรายการงานที่ต้องทำ
- ตรวจใบสมัครและสลิป: คิวรายการ, รายละเอียดใบสมัคร, ดูตัวอย่างไฟล์จำลอง, อนุมัติ หรือเลือกเทมเพลต “สลิปไม่ถูกต้อง” / “เปิดสลิปไม่ได้”
- ตั้งค่ารอบและศูนย์สอบ: นำเข้าศูนย์สอบตัวอย่าง กำหนดเวลาเปิด/ปิดสมัครและปิดแก้ไข สาธิตการล็อกชุดศูนย์เมื่อเปิดรับสมัคร และการสร้างเลข Heat หลังปิดรับสมัคร
- ผลสอบ Heat: เลือกไฟล์ตัวอย่างเป็นฉบับร่าง แสดงตัวอย่างผู้ผ่านและรายการจับคู่ผิด ให้แก้ข้อมูลใบสมัครหรือเปลี่ยนไฟล์ตัวอย่าง แล้วจึงยืนยันประกาศผล
- เลข Final: นำเข้ารายการตัวอย่าง แสดงรายการจับคู่สำเร็จ/ไม่พบ/จับคู่ได้หลายใบสมัคร และมีขั้นตอนจับคู่ด้วยมือใน prototype
- การซิงก์ชีต: แสดงสถานะซิงก์ และข้อความ “ไม่สามารถซิงก์ข้อมูลเข้าชีตได้ ตอนนี้ระบบกำลังพยายามซิงก์ข้อมูลอยู่” เมื่อจำลองข้อผิดพลาด โดยไม่มีปุ่มลองใหม่

## โครงสร้างและการนำทาง

หน้าแรกใช้แถบนำทางสาธารณะแบบเรียบง่าย โดยวางรายการสอบและปุ่มสมัครไว้เด่นก่อนคำอธิบายวิธีสมัคร; การ์ดแต่ละรายการแสดงกำหนดปิดรับแยกกันและส่งชื่อรอบที่เลือกไปยังฟอร์มสมัคร หน้า workflow อื่นใช้ shell สำหรับบัญชีและแอดมิน; เมื่อเปิดส่วนแอดมินใช้ sidebar แยกและมีตัวบอกชื่อรอบที่กำลังจัดการ บนมือถือเมนูหลักเลื่อนได้ในแนวนอน และ sidebar หลังบ้านยุบเป็นเมนูที่เปิดด้วยปุ่มมีชื่อและสถานะ expanded ชัดเจน

ต้นแบบมีตัวเลือก persona สำหรับสลับผู้ใช้ทั่วไป ผู้สมัคร ผู้ประสานงาน และแอดมิน เพื่อเข้าดูหน้าตามสิทธิ์ได้โดยไม่ต้องเชื่อมระบบยืนยันตัวตน ปุ่มและลิงก์หลักทุกตัวต้องพาไปหน้าหรือ state ที่สอดคล้องกัน; action ที่เป็นบริการจริงจะแสดง feedback ว่าถูกจำลอง

## ข้อมูลและกติกาสถานะ

- ใช้ข้อมูลตัวอย่างภาษาไทยและชื่อผู้เข้าสอบ/โรงเรียนภาษาอังกฤษให้สอดคล้องกับการค้นหาและ matching ใน requirements
- หน้า public ใช้สถานะทั่วไปเพียงสองค่าเท่านั้น: รออนุมัติ/ตรวจสอบสลิป และยืนยันใบสมัคร
- รายละเอียดปัญหาสลิปและลิงก์อัปโหลดแสดงในบริบทอีเมล/หน้าอัปโหลดและหลังบ้าน ไม่เปิดเผยในผลค้นหาสาธารณะ
- ใบสมัครแสดงเลข Heat หรือ Final เมื่อมี หากยังไม่มีเลข Final แสดง “รอเลขประจำตัว”; เลข Heat สาธิตรูปแบบรหัสศูนย์สอบ 3 หลักและลำดับ 4 หลัก
- การแก้ไขข้อมูลที่อนุญาตหลังอนุมัติไม่เปลี่ยนสถานะทั่วไปกลับเป็นรอตรวจ และการแก้จากบัญชีที่เข้าสู่ระบบไม่ถามเลขท้ายโทรศัพท์ซ้ำ
- ผลสอบที่ประกาศแล้วและการจับคู่เลขสอบที่ยืนยันแล้วมี feedback ว่าล็อกตามกติกา

## ภาษาภาพและการเข้าถึง

- หน้าแรกใช้โทนสว่างเป็นมิตร มีภาพประกอบจาก CSS และการ์ดรายการสอบที่แสดงสถานะ กำหนดปิดรับ และปุ่มสมัคร; ลำดับเนื้อหาอิงหน้าอ้างอิงวันเด็กฯ ที่ผู้ใช้ให้มา ส่วน workflow และหลังบ้านคงโทนการศึกษาที่น่าเชื่อถือ
- ใช้โลโก้ OCEC TH ที่ผู้ใช้ให้มาเป็นแบรนด์หลัก แล้วกำหนด palette จากสีในโลโก้: primary ม่วง #5955A8, ชมพู #DF3D69 และเหลือง #E9A522 โดยใช้ tint อ่อนในพื้นหลังและไอคอน; ใช้ primary กับปุ่มหลัก ข้อความปุ่มสีขาว, background #F8F7FB, card #FFFFFF, foreground #302E45 และ border #E6E4ED; สถานะผ่านใช้พื้น #DCFCE7 กับตัวอักษร #166534, สถานะรอใช้พื้น #FEF3C7 กับตัวอักษร #92400E, และข้อผิดพลาดใช้พื้น #FEE2E2 กับตัวอักษร #991B1B
- ใช้ semantic CSS variables แทนสีที่กระจายในแต่ละหน้า และใช้ Noto Sans Thai สำหรับภาษาไทย/อังกฤษ พร้อม system sans-serif fallback
- ขนาดตัวอักษรเนื้อหาเริ่มที่ 16px และ line-height อย่างน้อย 1.5; จำกัดความกว้างข้อความยาวบนจอใหญ่
- ใช้ไอคอน SVG ชุดเดียวกัน ไม่มี emoji แทนไอคอน; ไอคอนตกแต่งซ่อนจาก screen reader และปุ่มไอคอนมี accessible name
- ทุกฟอร์มมี label, คำใบ้และข้อผิดพลาดใกล้ช่องกรอก; keyboard focus ชัดเจน, ลิงก์ข้ามไปเนื้อหาหลัก, ปุ่มสูงอย่างน้อย 44px และไม่ใช้สีเพียงอย่างเดียวบอกสถานะ
- รองรับจอมือถือ แท็บเล็ต และ desktop โดยไม่มี horizontal overflow; เคารพ prefers-reduced-motion และให้ feedback สำหรับการส่งฟอร์มหรือ action ที่เปลี่ยน state

ชุดคำแนะนำ UI/UX ที่ใช้เป็นฐานมาจากผลค้นหา design-system “Accessible & Ethical” สำหรับ education/public portal และ typography “Thai Modern” (Noto Sans Thai) พร้อม React guidance เรื่อง controlled form inputs และ semantic accessible queries

## ขอบเขตและข้อยกเว้น

- ไม่มี backend, database, real Google authentication, real email, payment processing, file upload persistence หรือ Google Sheets sync
- ปุ่มนำเข้าไฟล์ใช้ข้อมูลตัวอย่าง/preview ฝั่งหน้าเว็บเท่านั้น ไม่เปลี่ยนไฟล์จริงหรือส่งไปบริการภายนอก
- การค้นหาและแก้ไขอาศัยข้อมูล mock; ไม่มีข้อมูลส่วนบุคคลจริง
- การตรวจความถูกต้องของ business rules ฝั่ง server และ security controls ต้องออกแบบแยกก่อน production

## เกณฑ์ตรวจรับดีไซน์

- ผู้ใช้เปิดหน้าแต่ละกลุ่มจาก navigation ได้โดยไม่ต้องพิมพ์ URL
- ผู้ใช้ทดลอง flow ค้นหาสถานะ, ค้นหาเพื่อแก้ไข, ดูใบสมัคร, ยืนยันสิทธิ์ Final, สมัคร Final และค้นหาผลสอบได้ด้วยข้อมูลตัวอย่าง
- แอดมินทดลองเปิดดูคิวตรวจ, ใช้เทมเพลตปัญหาสลิป, ดูผลนำเข้าฉบับร่าง/รายการขัดแย้ง, จับคู่เลข Final และเห็นข้อความซิงก์ไม่สำเร็จได้
- สถานะและช่องแก้ไขที่แสดงตรงกับข้อกำหนดใน OCEC-Portal-Requirements.md
- layout ปรับตาม viewport และ controls ใช้งานได้ด้วย keyboard พร้อม visible focus
